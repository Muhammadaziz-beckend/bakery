# Bakery — мультитенантная система управления пекарней

Веб-платформа для управления сетью пекарен: у каждой пекарни (организации)
своя витрина для клиентов на отдельном поддомене, свой склад, производство,
заказы, клиенты и долги поставщикам — всё изолировано друг от друга внутри
одной установки системы. Плюс общая внутренняя панель для сотрудников,
где всё это администрируется.

## Из чего состоит проект

```
bakery/
├── server/       # Django REST API (бэкенд, ядро системы)
├── web/          # Админ-панель для сотрудников пекарни (React)
├── client_web/   # Витрина-магазин для клиентов пекарни (React)
├── docs/         # Документация (деплой и т.п.)
└── ads/          # Маркетинговые/промо-материалы
```

Три отдельных приложения, объединённых одним API:

- **server** — Django 5.1 + Django REST Framework, отдаёт JSON API и
  раздаёт стандартную Django-админку для быстрого администрирования.
- **web** — панель для владельца/сотрудников пекарни: заказы,
  производство, склад, клиенты, отчёты, долги поставщикам, настройки.
  Один аккаунт сотрудника = одна организация (`User.organization`).
- **client_web** — публичная витрина, по которой конечные покупатели
  выбирают пекарню (или сразу попадают в неё по её поддомену), смотрят
  каталог и оформляют заказ.

## Мультитенантность: как это работает

Одна инсталляция бэкенда обслуживает сразу много пекарен
(`apps.organization.Organization`). Почти все модели (товары, склад,
заказы, клиенты, производство) наследуют `ParentalOrganization`
(`utils/models.py`) — то есть жёстко привязаны к конкретной организации,
и данные одной пекарни никогда не видны другой.

У каждой организации:

- свой **поддомен** (`Organization.slug` → `<slug>.<STOREFRONT_BASE_DOMAIN>`,
  например `ali.maximumcomfort.pro`) или свой собственный домен
  (`Organization.custom_domain`);
- при создании/переименовании/удалении организации бэкенд сам создаёт
  или удаляет DNS A-запись в **Cloudflare** и генерирует/удаляет nginx-конфиг
  под этот домен (`apps/organization/provisioning.py`,
  `utils/cloudflare.py`, `utils/nginx.py`) — вручную ничего прописывать не
  нужно;
- `client_web` собирается **один раз** с фиксированным адресом API
  (`VITE_API`) и раздаётся одинаково под любым поддоменом — какую именно
  организацию показывать, витрина определяет во время выполнения по
  хосту браузера (`Organization.resolve_by_host`,
  `PublicOrganizationResolveView`): если поддомен привязан к организации —
  сразу открывается её витрина, если нет (общий домен, `localhost`) —
  показывается список всех активных пекарен для выбора.

## Бэкенд (`server/`)

Django-приложения (`server/apps/`):

| Приложение     | За что отвечает |
|----------------|------------------|
| `account`      | Сотрудники пекарни. Кастомная модель `User` — логин по номеру телефона (`USERNAME_FIELD = "phone"`), не по email/username. Флаг `is_owner` — бизнес-роль владельца (может оформлять заказы сверх дневного лимита), не путать с `is_staff` (доступ в django-admin). |
| `organization` | Сами пекарни: название, логотип, адрес, поддомен/свой домен, флаг активности. Провижн DNS+nginx при создании/переименовании/удалении. |
| `warehouse`    | Склад: категории и товары (`Product`), варианты товаров (`ProductVariant` — например разные размеры торта, у каждого своя цена/рецептура/остаток), ингредиенты (`Ingredient`) с единицами измерения (`Unit`), рецептуры расхода сырья (`ProductConsumption`/`ProductVariantConsumption`), поставщики (`Supplier`) и приход сырья от них (`TransactionIngredient`). |
| `production`   | Производство партий готовой продукции (`ProductProduction`) — списывает сырьё со склада по рецептуре, считает срок годности по дате изготовления, отслеживает распроданность партии (`ProductProductionSoldItem`, FIFO-списание при завершении заказа). |
| `order`        | Заказы клиентов (`Order`/`OrderItem`) — статус (в ожидании/в процессе/готово/возврат), способ получения (самовывоз/доставка), статус оплаты. Дневной лимит заказов на товар (`Product.daily_order_limit`), который можно переопределить на конкретную дату (`ProductOrderLimitOverride`, например на праздник). |
| `client`       | CRM-карточки клиентов внутри организации. Может быть привязана к сквозному `CustomerAccount` (личный кабинет на витрине), если клиент когда-либо заказывал через сайт. |
| `debt`         | Долги перед поставщиками сырья (`DebtFromSupplier`) и история их погашения (`DebtFromSupplierItems`). |
| `storefront`   | Публичный API витрины: каталог организаций и товаров без авторизации, отдельная лёгкая аутентификация покупателей (`CustomerAccount`/`CustomerToken` — не связана с `account.User`, это разные системы логина для сотрудников и для покупателей), заказы покупателей. |

Аутентификация API — `Token` или `JWT` (переключается переменной
`AUTH_MODE` в `.env`: `token` / `jwt` / `both`), см. `core/config_drf.py`.
Документация API — Swagger/OpenAPI (`drf-yasg` + `drf-spectacular`),
доступна на `/api/v1/swagger/`.

## Админ-панель (`web/`)

React + Vite. Разделы (см. `web/src/App.jsx`):

- **Главная** — сводка/дашборд.
- **Заказы** — приём и обработка заказов клиентов.
- **Производство** — журнал партий, списание сырья, продажа партий.
- **Товары** и **Склад** — карточки товаров/вариантов, ингредиенты,
  остатки, приход сырья от поставщиков.
- **Клиенты** — CRM.
- **Долги** — долги перед поставщиками и их погашение.
- **Отчёты** — аналитика.
- **Настройки** — профиль организации (лого, адрес, поддомен и т.п.).

Один сотрудник видит и администрирует только свою организацию.

## Витрина (`client_web/`)

React + Vite. Публичная часть для клиентов пекарни:

- список пекарен на общем домене — либо сразу витрина конкретной пекарни,
  если открыта по её поддомену/домену (`/store/:orgId`);
- каталог товаров по категориям, корзина (хранится в `localStorage`,
  отдельно на каждую организацию — `context/CartContext.jsx`);
- регистрация/логин покупателя, личный кабинет, история заказов.

## Продакшен-инфраструктура

- Бэкенд — ASGI (`uvicorn`) за nginx-реверс-прокси, systemd-сервис.
- БД — SQLite по умолчанию (`server/core/database.py`; блок под
  PostgreSQL в файле есть, но закомментирован).
- Cloudflare — DNS + проксирование (HTTPS терминируется на Cloudflare,
  на origin-сервере отдельный SSL не настраивается).
- Подробная пошаговая инструкция по разворачиванию сервера (включая уже
  выловленные грабли — несовместимость Django с Python 3.14,
  игнорируемые git'ом миграции и т.п.) — **[docs/server-deployment.md](docs/server-deployment.md)**.

## Локальный запуск (разработка)

```bash
# Бэкенд
cd server
python3.12 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .envExenpl .env      # заполнить SECRET_KEY и т.д., DEBUG=True
python manage.py migrate
python manage.py runserver

# Админ-панель
cd web && npm install && npm run dev

# Витрина
cd client_web && npm install && npm run dev
```

Оба фронтенда по умолчанию ходят в API на `http://127.0.0.1:8000/api/v1/`
(`VITE_API` в соответствующем `.env`).
